## 1. 抜け漏れ（Omissions）

### 1.1 【重大】GitHub Pages ライブデモが計画のどこにも登場しない → M2-8 で確実に破壊される

`gh api repos/masnak/waveVisualizer/pages` で実設定を確認した結果:

```json
{
  "status": "built",
  "build_type": "legacy",
  "source": { "branch": "main", "path": "/" },
  "public": true,
  "html_url": "https://masnak.github.io/waveVisualizer/"
}
```

README.md 冒頭にも `Sample Page: https://masnak.github.io/waveVisualizer/` と明記されている。つまり **`main` ブランチのリポジトリルートを push の都度そのまま静的配信する「レガシー Pages」が現に稼働中** で、これは `index.html` が素の classic `<script src="./main.js">` 直参照だから成立している。

計画書全文（0〜3節、レビュー履歴含む）に "Pages" ないし「デプロイ」という語は一度も出てこない。しかし M2-8 で発生することは:

- `main.js` 等 4 ファイルが `src/` へ物理移動（1.2「ファイルの root → src/ 物理移動は M2-8 の一部」）
- `index.html` のエントリが `<script type="module" src="/src/main.ts">` に書き換わる
- B1 注記の通り「classic script のままでは vite build は成立しない」＝ **`vite build` で bundle された dist/ を配信しない限り、Pages のレガシー配信は動かない**

この状態で `main` に push すると、Pages は自動的に再ビルド・再公開する（レガシー方式は対象ブランチへの push が配信トリガー）。結果、`.ts` ファイルは正しい MIME type で配信されずブラウザの module スクリプトが拒否するか、単純に参照先ファイルが存在せず 404 になる。**M2-8 の最初のファイル移動コミットを push した時点で、現在稼働中の公開デモが壊れる。** M2-11 完了や M2-12 のドキュメント同期を待つ余地はない。

さらに副次的な技術要件として、Pages は `masnak.github.io/waveVisualizer/`（プロジェクトページ、サブパス配信）である以上、Vite の `vite.config` に **`base: '/waveVisualizer/'` を明示しないとビルド後のアセットパスがルート基準になり全滅する**（Vite + GitHub Pages の定番の踏み外しポイント）。これも計画のどこにも記載がない。

**推奨対応**（実装は別途相談でよいが、計画への明記を推奨）:
- M2-8 の「`vite build` 成功を確認」（計画書 1.2 節・M2-8 のステップ記述）の直後に、Pages を **GitHub Actions ベースのデプロイ**（`actions/upload-pages-artifact` + `actions/deploy-pages`、リポジトリ設定の Pages Source を "GitHub Actions" に切替）へ移行する作業を明示的に追加する
- `vite.config` に `base: '/waveVisualizer/'` を設定する
- **リポジトリルートからの静的ファイル撤去（src/ への物理移動）と、Pages デプロイ方式の切替は同一コミット/PR で atomic に行う**ことを完了基準に明記する（順序がずれると公開デモがダウンタイムを持つ）
- M1 or M2 の Done 基準に「ライブデモ URL が引き続き 200 で応答し、初期化〜録音〜解析が通ること」を1行追加する

これは 9 回のレビュー（Phase 3 専門家 4 名 + Phase 5 PM + Phase 6 専門家 4 名）のいずれも指摘しておらず、レビュアー全員が「アプリの内部構造」に焦点を当て「配信インフラ」を見ていなかったことによる盲点と考えられる。

### 1.2 【中】README.md の陳腐化ウィンドウが計画に存在しない

README.md は現状、以下を含む（実際に確認済み）:

計画は CLAUDE.md については M1-4 の直後に更新するゲートを明示している（1.1 節末尾および M1-4 のステップ記述）が、**README.md の更新は M2-12（最終ドキュメント同期）まで一切ゲートがない**。M1 完了〜M2-11 完了までの間、README の「ローカル実行方法」と「ファイル構成」は実態と乖離した状態が続く。これは意図的な先送りなのか、単なる見落としなのか、計画上の言及がないため判別できない。

**推奨対応**: 少なくとも M1-4（起動コマンド変更点）は CLAUDE.md と同時に README.md の該当セクションも更新するか、あるいは「README は M2-12 まで意図的に据え置く」と明記して既知の陳腐化として扱う（計画は B3 注記のように「意図的に許容する不整合」を明示する文化があるため、この整合性を取るのが自然）。

## 2. セキュリティホール

計画由来の新規セキュリティホールは見つからなかった。確認した論拠:

- devDependencies 9 個限定・lockfile コミット・CI は `npm ci`（サプライチェーンの再現性確保）
- CI `permissions: contents: read` の最小権限が明記されている
- secrets 不使用（デプロイ等の機微操作がそもそも計画に存在しない ＝ 1.1 の Pages 抜け漏れが解消されると新たに `pages: write` `id-token: write` の権限追加が必要になる点は要留意）
- アプリ自体はクライアント完結（マイク音声はローカル処理のみで外部送信なし）で、`innerHTML` 使用箇所（`sinewaveAnalyser.js:539,550` 等）も静的テンプレートで外部入力の埋め込みがなく XSS ベクタにはならないことを確認済み
- console.error の allowlist 対象は静的解析上も spectrumVisualizer.js:142 の `🚨 20kHz超` 診断 1 件のみで、他の `console.error` 呼び出し（grep で全 19 件確認）はすべて catch 節内のエラーパスであり、計画の想定と一致

**任意の追加ハードニング候補**（必須ではない。Phase 5 PM 精査で「CI ハードニング超過」を意図的にスリム化した方針と整合させるため、あくまでオプション扱いで記載）:
- GitHub Actions を `@v4` のようなタグ指定ではなく commit SHA 固定にする。ただし non-secrets・非デプロイ用途の現状 CI ではリスクは低く、上記 1.1 の対応で `pages: write` 権限が入る場合は再検討の価値あり
- Dependabot / `npm audit` の定期実行。個人のホビープロジェクト規模では過剰と判断しても妥当

## 3. 部分最適 vs 全体最適

- **最大の事例は 1.1 の GitHub Pages。** 計画はテスト基盤・TS 移行という「アプリ内部の正しさ」に極めて高い解像度で最適化されている一方、「このアプリが今まさに公開ホスティングされている」という全体像が抜け落ちていた。個々のステップ（M2-8 の ESM 化、src/ 移設）は単体では正しいが、デプロイ設定という外部要因と組み合わさった瞬間に破壊的になる、という教科書的なパターン
- それ以外の観点では、部分最適の弊害は見当たらない。むしろ計画は「部分最適が全体を壊す」パターンを内部的には強く警戒した設計になっている:
  - state.ts を「グローバル変数の引っ越し」にしない設計（1.4-A）は、各ファイルを個別にモジュール化する際に生じがちな「動くように見えて設計が破綻する」典型的な部分最適の罠を明示的に回避している
  - golden-vector を M2 冒頭に前倒しし、以降の全リファクタの安全網にする設計は、「今のステップだけ通ればいい」という近視眼を防ぐ良い全体最適化
  - console.error allowlist を「絵文字なら許容」のような包括条件ではなく実観測の厳密列挙にする、という決定（1.4-B）も、目先のテスト通過を優先して将来のエラーを握りつぶす部分最適を明示的に禁止している

総じて、アプリ内部設計に関しては全体最適的な視点が行き届いている一方、デプロイという「境界の外側」への視点が欠けていた、というのが今回の総括。

## 4. 実装順序（手戻りの少なさ）

マクロな順序（M1-1〜M1-6 → M2-7〜M2-12）は手戻り最小化の観点で妥当と判断した。根拠:

- **安全網 → 最大リスク → ツール交換 → リファクタ**の順は定石通り。特に「CI-smoke を M1-3 に前倒し」（Linux headless 録音経路という最大の単一失敗点を最初に踏む）は、Phase 6 で DevOps Automator が指摘した「最大リスクが M1 末尾にあるのは矛盾」を正しく解消済み
- M2-7（dsp.ts + golden-vector をアプリ未接続のまま独立モジュールとして先に固定）は、Phase 3 で Software Architect が指摘した「ステップの big-bang 化」を避ける良い設計。抽出時の変換を「maxAmplitude のグローバル書込→戻り値化」の 1 点のみに限定し、golden-vector がその 1 点も含めて検証する、という一貫性も確認した
- M2-8 の ESM 変換順（waveVisualizer → spectrumVisualizer → sinewaveAnalyser → main、葉→根）について、依存関係を実コードで検証した:
  - `sinewaveAnalyser.js` は実は 4 ファイル中もっとも `main.js` のグローバル（`audioContext` / `recordedChunks` / `micSoundAnalyser` / `waveVisualizer` / `spectrumVisualizer`）へ依存度が高く、真の「末端」は waveVisualizer/spectrumVisualizer 側という計画の順序付けは正しい
  - window ブリッジ方式（module 化後に `window.X = X` で公開）は、classic script 側の裸の識別子参照がグローバルオブジェクト（window）のプロパティ解決も経由するため技術的に成立する。これは検証に値する非自明な点だったが、問題なしと確認できた
  - ただし 1 点、**ES module（`type="module"`）は `defer` 相当で実行が遅延される一方、既存の classic script は同期実行**という違いがある。理論上、変換途中の中間状態でモジュール側のトップレベルコードに未変換 classic 側の即時実行結果が必要な箇所があれば実行順が崩れる可能性がある。実コードを確認した限り、4 ファイルとも「他ファイルの値を読むトップレベル（同期）コード」は存在せず、すべてクリック等のユーザー操作後のイベントハンドラ内でのみ他ファイルの値を参照するため、**このアプリに関しては実害は出ないと判断した**。ただし非自明な ESM の仕様上の罠であり、計画の 1.4-F に一行、この点を明記しておくと実装時に無用な混乱を避けられる（低優先度の改善提案）
- M2-9（init() 集約）を M2-8（ESM 化）の後に置く順序も適切。ESM 化と副作用集約を同時にやらないことで、Phase 3 で指摘された「big-bang」リスクを二重に回避している

**唯一の順序修正提案**: 1.1 で指摘した GitHub Pages 対応は、M2-8 の「`src/` へのファイル物理移動」と**同一コミット/PR で atomic に**行う必要がある。現在の計画のどこに挿入しても良いが、遅くとも M2-8 完了以前、かつ物理移動コミットと不可分にする、という制約を明記すべき。
