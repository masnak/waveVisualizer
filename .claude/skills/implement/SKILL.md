# Implement スキル

現状確認 → 計画提示 → テストファースト TDD → 検証の一連フローで機能を実装する。

> **移植元について**: 本スキルは `makerkit/course` リポジトリの同名スキルを、このリポジトリ（TypeScript strict + Vite、単一パッケージ、DB/ADR/CoDD/TDAD なし）向けに書き換えたもの。元のスキルは Turborepo モノレポ・Supabase・独自の CoDD/ADR/TDAD ツールチェーンに強く依存しており、そのままでは動作しない。

## 基本原則

- **テストファースト**: 必ずテストを先に書き、RED → GREEN → REFACTOR で進める
- **スモールステップ**: 1 ステップ = 1 テスト + 1 実装。大きな変更を一度に行わない
- **日本語での意図表示**: テストの意図（なぜこのテストか）と実装の意図（なぜこう実装するか）を必ず画面に日本語で表示する
- **細かい確認**: ステップごとにテストを実行し、通過を確認してから次へ進む
- **フェーズ完了まで続行**: ユーザーの明示的な中断指示がない限り、フェーズを最後まで実行する

## 実行手順

### Phase 0: 現状確認

Phase 0 の調査は **1 つのサブエージェント（Agent, subagent_type=Explore）に全委譲** する。メインコンテキストには構造化された要約のみを返す。

#### サブエージェントへの指示

以下の全項目を調査し、構造化出力テンプレートの形式で結果を返すよう指示する:

- CLAUDE.md を参照し、タスクに関連する技術仕様・制約（Web Audio API / Canvas 2D API / MediaDevices の挙動、`AppContext`/`state.ts` の注入依存・残余共有状態の設計原則）を把握する
- Agent (subagent_type=Explore) で関連ファイル・既存パターン・依存関係を調査する（`src/audio/` の純粋関数群、`src/visualizers/`、`sinewaveAnalyser.ts` のオーケストレーション層等、責務境界を把握する）
- 対象ファイルに対応する既存テスト（`src/**/*.test.ts` の Vitest 単体テスト、`e2e/workflow.spec.ts` の Playwright E2E）を Grep/Glob で検索し、一覧化する
- `dsp.ts` 等の golden-vector 保護テストに触れる変更の場合、その旨を明記する（許容誤差が厳しく設定されているため）

#### 構造化出力テンプレート（サブエージェントの返却形式）

```
## Phase 0 調査結果
### 関連ファイル: [パスと役割の一覧]
### 既存テスト:
  - 対象ファイルに対応するテストファイルの相対パス一覧（Vitest / Playwright E2E）
  - golden-vector 等の回帰保護テストに触れる場合はその旨
### Phase 2 で参照が必要なファイルパス一覧: [パスリスト]
### 実装上の制約・注意点: [3 項目以内。AppContext 注入 / state.ts 残余共有状態 / DOM・AudioContext 副作用境界等]
```

**コンテキスト軽量化**: サブエージェントはファイル全文をそのまま含めず、上記の要約形式に圧縮して返すこと。メインコンテキストには要約のみが入る。

サブエージェントの結果を受け取り、メインコンテキストに表示する。Phase 1 の計画書「依存関係・影響範囲」セクションに反映する。

### フェーズ区切りの進捗管理表アップデート

**各フェーズの完了時に、必ず以下の進捗管理表を画面に表示する:**

```
## 📊 進捗管理表

| Phase | 状態 | 完了日時 | 備考 |
|---|---|---|---|
| Phase 0: 現状確認 | ✅ 完了 / 🔄 進行中 / ⬜ 未着手 | HH:MM | メモ |
| Phase 1: 修正計画の提示 | ✅ / 🔄 / ⬜ | | |
| Phase 2: テストファースト TDD | ✅ / 🔄 / ⬜ | | ステップ N/M |
| Phase 3: 統合検証 | ✅ / 🔄 / ⬜ | | |
| Intent-Failure チェック | ✅ / 🔄 / ⬜ | | |
| Phase 4: 完了報告 | ✅ / 🔄 / ⬜ | | |
```

- フェーズ開始時に当該行を 🔄 に更新して表示する
- フェーズ完了時に当該行を ✅ に更新して表示する
- Phase 2 では TDD ステップの進捗（例: ステップ 3/5）も備考欄に記載する

### Phase 1: 修正計画の提示

1. **計画書の作成**: `.ai-workspace/yyyymmdd-NNN-タイトル.md` に計画書を保存する（NNN は日付ごとに 000 からリセット。命名規則は `.ai-workspace/000-ai-progress-management-guide.mdc` 参照）

**計画書テンプレート**:

```markdown
# [タスクタイトル]

作成日: YYYY-MM-DD

## 概要

[タスクの目的と背景を 2-3 文で]

## 調査結果

### 関連ファイル

| ファイル | 役割 | 変更内容 |
|---|---|---|
| path/to/file | 説明 | 追加/変更/削除 |

### 依存関係・影響範囲

[変更が影響するコンポーネントや機能。AppContext 注入・state.ts 残余共有状態・DOM/AudioContext 副作用境界への影響を含む]

## TDD 実装ステップ

| # | テスト（RED） | 実装（GREEN） | 検証 |
|---|---|---|---|
| 1 | テストの説明 | 実装の説明 | vitest / playwright |
| 2 | ... | ... | ... |

## 4 観点チェック

| 観点 | 評価 | 備考 |
|---|---|---|
| 堅牢 | ✅/⚠️ | コメント |
| セキュア | ✅/⚠️ | コメント |
| 明快 | ✅/⚠️ | コメント |
| 修正容易 | ✅/⚠️ | コメント |
```

2. **タスク登録**: TDD ステップを TaskCreate でタスク登録する
3. **ユーザー承認**: 計画を画面に要約表示し、承認を待つ

### Phase 2: テストファースト TDD 実装

#### 巻き戻しルール

同一テストファイルの Red→Green サイクルが **2 回連続で失敗** した場合、そのステップの実装を中断する。失敗原因を 1-2 文で記録し、Phase 1 の **該当ステップのみ** を再設計する。再設計時は失敗原因を制約条件として明示すること。Phase 1 全体の再設計は不要。

各ステップで以下のサイクルを繰り返す:

#### Step N-0: 関連テストの確認

Phase 0 で洗い出した既存テスト一覧（Vitest / Playwright E2E）のうち、当該ステップの変更対象に関係するものを確認する。新規に見つかったテストがあれば Grep で軽く探索する（この規模のリポジトリでは自動検出ツールは不要、目視確認で十分）。

検出したテストは:
- Step N-a: 新規テスト作成時の重複回避に使用
- Step N-b: GREEN 確認時にリグレッションチェックとして実行

#### Step N-a: テスト作成（RED）

1. **テストの意図を表示**:
   ```
   📝 テスト: [テスト名]
   意図: [なぜこのテストが必要か — 日本語で説明]
   期待: [このテストが保証すること]
   ```
2. テストコードを作成する（純粋関数は `src/audio/*.test.ts` に Vitest、DOM/AudioContext 絡みのフローは `e2e/workflow.spec.ts` に Playwright E2E）
3. テストを実行し、**失敗すること（RED）を確認する**
   ```bash
   pnpm test <test-file>             # Vitest（-- を挟むとフィルタが効かないため付けない）
   pnpm exec playwright test <spec>  # Playwright E2E
   ```
4. RED を確認した旨を画面に表示する

#### Step N-b: 実装（GREEN）

1. **実装の意図を表示**:
   ```
   🔨 実装: [変更対象]
   意図: [なぜこの実装方法を選んだか — 日本語で説明]
   変更: [具体的な変更内容の要約]
   ```
2. テストを通すための最小限の実装を行う
3. テストを実行し、**通過すること（GREEN）を確認する**
4. **リグレッションゲート**: Step N-0 で検出した既存テストを全て実行し、GREEN を確認する。**既存テストに RED がある場合、そのテストを修正するまで次ステップに進んではならない**
5. GREEN を確認した旨を画面に表示する

#### Step N-c: リファクタリング（任意）

- コードの品質改善が必要な場合のみ実施
- リファクタリング後もテストが通ることを確認する

#### Step N-d: 進捗更新

- TaskUpdate で当該タスクを completed にする
- 計画書のチェックリストを更新する（`[ ]` → `[x]`）

### Phase 3: 統合検証

#### 3-a: 全体コマンド検証

```bash
pnpm run typecheck
pnpm run lint
pnpm run format:check
pnpm test
```

失敗があれば修正してから次へ進む。この時点で既存テストの破壊を確実に検出する。

#### 3-b: UI / フロー変更がある場合

- **視覚検証**: dev サーバー起動中（`pnpm run dev`）に `/mite` スキルでスクリーンショットを取得し、視覚的に確認する
  - 問題があれば修正（最大 3 回、同一問題 2 回でエスカレーション）
- **ブラウザ手動検証ループ**（CLAUDE.md「ブラウザ自動検証」参照）: 「初期化」→「録音開始」→「周波解析」→ 成分選択 →「合成再生」を通し、コンソールエラーがないことを確認する

```bash
# E2E テスト（Playwright、フェイクマイクデバイスフラグで自動設定済み）
pnpm run test:e2e
```

- 対象のフローに既存の E2E テストがある場合は必ず実行する
- 新規フローの場合は E2E テストの追加を検討し、必要に応じて `e2e/workflow.spec.ts` に作成する

#### 3-c: ビルド検証

```bash
pnpm run build
```

#### 3-d: テスト実行メニュー

実装内容に応じて、ユーザーに実行するテストを選択させる:

```
## 🧪 テスト実行メニュー

実装内容に基づき、以下のテストを実行できます。
実行するテストを選んでください（複数選択可）:

1. ✅ typecheck/lint/format:check/test 済み（3-a で実行完了）
2. ⬜ E2E Playwright（エンドツーエンド）  — UI/フロー変更時に推奨
3. ⬜ build（本番ビルド確認）            — 最終確認に推奨
4. ⬜ すべて実行
```

- AskUserQuestion ツールで選択肢を提示する
- 実装内容から推奨テストを判定し、推奨マーク（推奨）を付ける
- 「すべて実行」選択時は typecheck → lint → format:check → test → test:e2e → build の順で実行する

#### 3-e: 結果の報告

検証結果を日本語で報告する:

```
## 検証結果

### テスト
- Vitest: PASS / FAIL (N tests)
- Playwright E2E: PASS / FAIL (N tests) ※UI/フロー変更時のみ

### 品質
- TypeCheck: PASS / FAIL
- Lint: PASS / FAIL
- Format: PASS / FAIL
- Build: PASS / FAIL

### 失敗がある場合
- 原因: [説明]
- 対応: [修正内容]
```

失敗がある場合は修正して再検証する。全て PASS するまでこのフェーズを繰り返す。

### Intent-Failure チェック

- `intent-failure-checker` agent を Agent ツールで起動する
- 入力: ユーザーの元の依頼文、変更ファイル一覧、計画書パス
- 結果が FAIL の場合: 問題を修正してから Phase 4 に進む
- 結果が WARNING の場合: ユーザーに報告し確認を取る

### Phase 3.5: CLAUDE.md 整合チェック

実装完了後、変更内容が CLAUDE.md の記述（プロジェクト構成・ボタン/キャンバス仕様・技術仕様）と齟齬をきたしていないか確認する。齟齬があれば CLAUDE.md を更新する（M2-12 で確立した「記載コマンド・構成は実態と一致させる」運用に従う）。

### Phase 4: 完了報告

1. 実装内容の要約を日本語で表示する
2. 計画書に完了マークを追記する
3. 変更ファイルの一覧を表示する
4. CLAUDE.md を更新した場合はその旨を明記する

## テスト種別の判定

実装対象に応じてテストランナーを選択する:

| 対象 | テストランナー | コマンド |
|---|---|---|
| 純粋関数（`src/audio/*.ts` の DSP・信号処理・合成計算） | Vitest | `pnpm test` |
| DOM/AudioContext 絡みのオーケストレーション（`sinewaveAnalyser.ts`・`main.ts`） | Vitest（可能な範囲）+ Playwright E2E | `pnpm test` / `pnpm run test:e2e` |
| ブラウザ E2E フロー（初期化→録音→解析→合成） | Playwright | `pnpm run test:e2e` |

## 注意事項

- 全ての進行報告・意図説明は**日本語**で行う（技術用語・コマンド名は英語可）
- `any` 型は使用禁止。`unknown` を使用する（`tsconfig.json` strict 設定）
- CLAUDE.md の 4 観点（堅牢・セキュア・明快・修正容易）を常に意識する
- テストの RED 確認をスキップしない。テストが最初から通る場合はテストの妥当性を疑う
- 計画書・タスク管理（TaskCreate/TaskUpdate）の両方を更新して進捗を追跡可能にする
- `audio/dsp.ts` 等の golden-vector テストは許容誤差が厳しく（`rel 1e-6`）設定されている。触れる場合は意図的な変更であることを明示する
