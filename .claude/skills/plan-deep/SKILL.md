# Plan Deep: 多段レビュー型計画スキル

計画を複数フェーズで練り上げ、専門エージェントのレビューと PM の精査を経て最終版を作成する。

ultrathink

## 実行フロー

```
Phase 1: ドラフト作成                        → ドラフト
Phase 2: 曖昧点の洗い出し + 仕様調整          → 仕様修正版
    ← ユーザー確認（仕様確定）
Phase 3: 専門エージェントレビュー
Phase 4: フィードバック反映                   → エージェントレビュー版
    ← ユーザー確認
Phase 5: PM 精査 + ユーザーとディスカッション  → PM レビュー版
    + 進捗管理表の作成
Phase 6: 最終レビュー（エージェント再呼出）    → 最終版
    + 必要に応じて進捗管理表をアップデート
    ← ユーザー承認 → 実装開始可
```

### ステータス遷移

| ステータス | Phase | 次のアクション |
|---|---|---|
| ドラフト | 1 | 曖昧点の洗い出しへ |
| 仕様修正版 | 2 | ユーザー確認後、エージェントレビューへ |
| エージェントレビュー版 | 4 | ユーザー確認後、PM 精査へ |
| PM レビュー版 | 5 | 最終レビューへ |
| 最終版 | 6 | ユーザー承認後、実装開始可 |

---

## Phase 1: ドラフト作成

### 1-1. タスクの理解

- ユーザーの要求（`$ARGUMENTS`）を正確に把握する
- 不明点があれば **この時点で** 質問する（後フェーズに曖昧さを持ち越さない）
- タスクの種類を判定: 機能実装 / バグ修正 / リファクタリング / インフラ / その他

### 1-2. コードベース調査

#### CLAUDE.md の確認
- `CLAUDE.md` を読み、対象機能の仕様・ボタン/キャンバス構成・技術仕様の制約を把握する
- 過去の関連計画・レポートが `.ai-workspace/` にあれば参照する

#### コードベース探索
Agent (subagent_type=Explore) で以下を調査する。**コンテキスト軽量化**: 生出力はサブエージェント内で処理し、メインには要約形式のみ返すこと。

1. **関連ファイルの特定**: タスクに関わるファイル・関数・クラス
2. **既存パターンの確認**: 類似の実装がすでにあるか（既存の可視化クラス・再生関数等）
3. **制約の確認**: Web Audio API / Canvas / MediaDevices の挙動、グローバル変数の共有状態
4. **依存関係**: 変更が影響する関数・UI 要素（本リポジトリは `<script src>` 読み込みのグローバル関数構成のため、**script の読み込み順とグローバル変数の参照関係**を必ず確認する）

### 1-3. ドラフト計画書の作成

`.ai-workspace/templates/plan-template.md` を読み込み、テンプレートに従って計画書を作成する。以下を追加・変更する:

- **ステータス行**: `ステータス: ドラフト` で開始（遷移: ドラフト → 仕様修正版 → エージェントレビュー版 → PM レビュー版 → 最終版）
- **レビュー履歴セクション**: 末尾に追加（Phase 3 以降で追記）

**ファイル名規則**: `YYYYMMDD-NNN-タイトル-plan.md`
- `NNN`: 000 から開始。同日の `.ai-workspace/YYYYMMDD-*` を確認して採番。日付が変われば 000 にリセット
- 対応する進捗ログは同じ NNN を使う（例: `progress-20260316-000-xxx.md`）

**保存先**: `.ai-workspace/`

ドラフト作成後、ユーザーに概要を伝える。

---

## Phase 2: 曖昧点の洗い出し + 実装提案

### 2-1. 仕様の曖昧点を特定

ドラフトを読み返し、以下を探す:

- **未定義の振る舞い**: 「エラー時はどうする？」「上限は？」「録音前に押されたら？」
- **暗黙の前提**: 明文化されていない想定（サンプルレート、ブラウザ、マイク権限等）
- **選択肢が残っている箇所**: 複数のアプローチが考えられる部分
- **影響範囲の不確実性**: 変更が予期しない箇所に波及する可能性（グローバル状態の共有）

### 2-2. 実装提案の挿入

各曖昧点に対して、計画書テンプレートのセクション 1「仕様決定」の形式に従い:

1. **問題を明記**: 何が曖昧か
2. **選択肢を列挙**: 各アプローチのメリット・デメリット
3. **推奨案を提示**: 4 観点（堅牢/セキュア/明快/修正容易）で根拠を明示
4. **対案がある場合**: 推奨案より優れているポイントを明示

### 2-3. ユーザーへの意思決定依頼

未確定事項をユーザーに確認する際は、**各確認事項ごとに以下の 3 点を必ず説明する**:

1. **意味**: その選択が技術的に何を意味するか。選択肢がある場合は各案を列挙し、4 観点（堅牢/セキュア/明快/修正容易）で推奨案と根拠を提示する
2. **影響範囲**: その選択が影響するファイル・機能・他の仕様決定。短期・中長期のトレードオフを含める
3. **推奨解決策**: 推奨案を明示し、なぜその案が最適かを具体的に説明する

**「どちらにしますか？」だけで聞かない。** ユーザーが判断できる十分な材料を揃えた上で、推奨案を添えて提示する。確認事項が複数ある場合は、事項ごとに上記 3 点を個別に説明する。

結果は計画書のセクション 1「仕様決定」に記載する。

### 2-4. ユーザーに提示して確認

ユーザーの回答を計画書に反映し、**ステータスを「仕様修正版」に更新**する。ユーザーが仕様を確定するまで、追加の調整を繰り返してよい。

**ユーザーの確認（仕様確定）なしに Phase 3 に進まないこと。**

---

## Phase 3: 専門エージェントによるレビュー

### 3-1. レビュアーの選定

計画の内容に基づき、利用可能なエージェントから適切なレビュアーを選ぶ。

**選定基準**:
- UI / フロントエンド → `Frontend Developer`、`UI Designer`、`UX Architect`、`UX Researcher`
- アクセシビリティ → `Accessibility Auditor`
- アーキテクチャ → `Software Architect`、`Workflow Architect`
- セキュリティ → `Security Engineer`
- コードレビュー → `Code Reviewer`
- テスト・検証 → `Test Results Analyzer`、`Evidence Collector`
- パフォーマンス → `Performance Benchmarker`
- ドキュメント → `Technical Writer`

**最低 2 名、最大 8 名**。無関係なエージェントは呼ばない。音声信号処理（DFT・位相・合成）の妥当性は特定エージェントの専門外のため、必要なら `general-purpose` に調査観点を明示して依頼する。

### 3-2. レビュー依頼

選定したエージェントを **Agent ツールで並列起動** する。起動時は各呼び出しに **`model: opus` を明示指定** する（グローバルエージェントは model 未指定のためセッションモデルを継承し過剰コストになる。レビューは高推論モデル = opus が適正）。各エージェントには計画書のパスと内容、レビュー観点、「計画のレビューであり実装ではない」ことを伝える。

---

## Phase 4: レビュー統合

### 4-1. フィードバックの統合

| 分類 | 対応 |
|---|---|
| **合意事項** | 計画に即座に反映 |
| **矛盾する指摘** | 両方の根拠を記載し、推奨案を提示 |
| **追加提案** | 必要性を評価して取り込み判断 |

### 4-2. 計画書の更新

フィードバックを反映し、**ステータスを「エージェントレビュー版」に更新**する。

- レビュー履歴に Phase 3 結果を追記（レビュアー / 指摘概要 / 対応）
- `Development Philosophy Check` セクションに 4 観点の評価を記入

### 4-3. ユーザーに更新版を提示

変更点を簡潔にまとめて報告。矛盾する指摘がある場合はユーザーに判断を求める。

**ユーザーの確認なしに Phase 5 に進まないこと。**

---

## Phase 5: PM 精査

### 5-1. PM エージェントによる精査

`plan-pm` エージェントを Agent ツールで起動する。渡す情報:
- 計画書の全文
- 元のタスク要求（`$ARGUMENTS`）
- Phase 2 で解消した曖昧点のリスト
- Phase 4 のレビュー結果サマリ

### 5-2. PM レポートをユーザーに提示

PM が挙げたディスカッションポイントについて、ユーザーと対話する。

### 5-3. PM レビュー版の確定

対話結果を反映し、**ステータスを「PM レビュー版」に更新**する。不要と判断されたステップを削除し、PM 精査結果をレビュー履歴に追記。

### 5-4. 進捗管理表の作成 ⚠️ 必須 — スキップ禁止

> **WARNING**: この手順を飛ばしがちなので注意。PM レビュー版の確定後、Phase 6 に進む前に必ず進捗管理表を作成すること。進捗管理表なしで Phase 6 や実装に進んではならない。

`.ai-workspace/templates/progress-template.md` と `.ai-workspace/000-ai-progress-management-guide.mdc` のテンプレートに従い、進捗管理ファイルを作成する。

**ファイル名**: `progress-YYYYMMDD-NNN-タイトル.md`（計画書と同じ NNN を使用）

含める内容:
- 計画書の作業ステップをフェーズ進捗として転記
- 各ステップの完了基準を検証チェックリストに転記
- 品質保証チェックリスト（コード品質・動作品質・記録品質）
- 問題・エラー記録セクション（空で準備）

**実装開始後は、ステップ完了ごとに進捗管理表を更新する。**

**セルフチェック**: 進捗管理表ファイルが `.ai-workspace/` に存在することを確認してから Phase 6 に進む。

---

## Phase 6: 最終レビュー

### 6-1. エージェントによる実装前最終レビュー

Phase 3 で選定したエージェント（または再選定）を **Agent ツールで並列起動** する（Phase 3-2 と同様、各呼び出しに **`model: opus` を明示指定**）。レビュー指示:

> 実装前の最終レビューです。以下の視点ごとに詳細にチェックしてレポートしてください。
>
> 1. **抜け漏れ**: 計画に記載されていないが必要な作業・考慮事項はないか
> 2. **セキュリティ・堅牢性ホール**: 入力検証、情報露出、グローバル状態の競合、ブラウザ間差異に穴はないか
> 3. **全体最適**: 部分最適を考慮するあまり、全体のアーキテクチャ・一貫性が壊れていないか
> 4. **実装順の妥当性**: 手戻りが最小になる順序に整理されているか。依存関係に矛盾はないか

### 6-2. 最終レビュー結果の統合

レビュー履歴に Phase 6 結果を追記（レビュアー / 視点 / 指摘概要 / 対応）。

### 6-3. 最終版の確定

レビュー結果を反映し、**ステータスを「最終版」に更新**する。実装順の調整があれば作業ステップを並べ替え。

### 6-4. 進捗管理表のアップデート

最終レビューで作業ステップや完了基準に変更があった場合、Phase 5 で作成済みの進捗管理表を更新する。

### 6-5. 成果物の出力 — 全項目チェック必須

以下の 4 成果物が全て揃っていることを確認する。**1 つでも欠けていたら実装に進まない。**

1. **計画書**: `.ai-workspace/YYYYMMDD-NNN-*-plan.md`（ステータス: 最終版）
2. **進捗管理表**: `.ai-workspace/progress-YYYYMMDD-NNN-*.md` ⚠️ 忘れやすい — 必ず存在確認
3. **タスクリスト**: TodoWrite で実装ステップを登録
4. **サマリ**: チャットに最終計画の概要を表示

**ユーザーの承認なしに実装を開始しないこと。**

---

## 注意事項

- 各フェーズの間で**必ずユーザーの確認を取る**（Phase 2→3、Phase 4→5）
- 計画書は**日本語**で記述する（技術用語・コマンド名は英語可）
- 簡易な計画には Claude Code 組み込みの Plan Mode を、精密な計画には本スキルを使う
